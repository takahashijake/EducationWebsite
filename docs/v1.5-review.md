# V1.5 review: interactive dynamic programming

## Published learning experience

The existing permanent `dynamic-programming` topic is now published in Algorithms. Recursion, Arrays and Strings, and Big O are advisory prerequisites. The lesson asks learners to define a state, base cases, recurrence, dependencies, and final answer before coding. It explains overlapping subproblems, optimal substructure where a best choice uses solved smaller states, when caching is useful, and when it adds no benefit. It distinguishes finding a value from reconstructing a solution. Three knowledge checks and links back to prerequisite lessons accompany worked staircase, coin, and knapsack examples.

Staircase counting uses `ways(0)=ways(1)=1` and `ways(n)=ways(n−1)+ways(n−2)` for n≥2. The empty staircase has one do-nothing arrangement. Memoization computes each distinct state once with O(n) cache and O(n) recursive stack space; tabulation fills from small to large in O(n) time and O(n) table space. Two running values suffice for only the final staircase count. Naive recursion can repeat states exponentially.

Unbounded minimum coin change uses `best[0]=0`, a distinct unreachable marker, and a minimum over reachable `best[a−coin]+1` candidates. [1,3,4] at target 6 demonstrates greedy failure: 3+3 beats 4+1+1. Sorted distinct denominations and strict improvements make ties keep the smaller coin. Saved parent coins reconstruct an optimal combination. Time is O(TK) for target T and K denominations; the count and parent arrays take O(T) space.

Zero-one knapsack uses `table[i][c]` for the first i items and capacity c. Include and exclude read the previous item row, so an item identity is never reused. Equal values exclude the later item. Backtracking through the full table returns selected IDs in input order. O(nC) time and O(nC) table space assume integer capacity C; the bound is pseudo-polynomial in C's bit length. A value-only descending-capacity update can use O(C) space, but the full table supports reconstruction and teaching.

## Engine and player contracts

`src/lib/dynamic-programming-steps.ts` is pure, deterministic, and React independent. Staircase targets are 0–15; the naive tree expands only for n≤10. Coin targets are 0–20, with 1–6 entered positive denominations each ≤20; duplicates are normalized and sorted. Knapsack capacity is 0–15, with at most six uniquely identified items, positive weights ≤15, and nonnegative values ≤30. All numeric inputs must be safe integers. A trace is capped at 450 frozen snapshots. Inputs are copied; external arrays are not mutated.

Snapshots record current state, dependencies, candidates, decisions, table, memo, selected items, and narration. The coin player labels future null cells as unfilled and only finalized null cells as unreachable. The player offers curated scenarios and a validated bounded composer, forward/back/reset controls, predictions before reveal, instrumented naive/memo call counts and cache hits, textual tables, and solution reconstruction. A call listing records parent links and repeated states for the bounded recursion tree. Controls work by keyboard; focus states reuse the existing design system. The interface uses text alongside highlighting, live narration, bounded table scrolling, and mobile containment. No timed animation is essential. The player traces only its local engine, not Code Lab Python, and its predictions do not award positive evidence.

## Practice and stable identity

Six browser Python labs have permanent IDs `dp-repeated`, `dp-memo`, `dp-table`, `dp-coin-count`, `dp-coin-solution`, and `dp-knapsack`. Each has a defective starter, two deterministic public checks, progressive hints, a reference, explanation, and reflection. Trusted Python regression checks run every reference and confirm each starter fails. Six permanent skills are `dp-overlapping-subproblems`, `dp-state-recurrence`, `dp-memoization`, `dp-tabulation-order`, `dp-coin-change`, and `dp-knapsack-reconstruction`. Twelve focused retrieval questions and twelve seeded adaptive families map these ideas to the existing five-question session and remediation links. New lesson checks and Python activity IDs have separate evidence mappings.

The same version-1 browser keys, record formats, old activity IDs, routes, reading completion, project progress, and coding drafts remain in use. The new topic increases the published denominator from 18 to 19 without deleting earned completions. Hinted or revealed Python solutions and assisted adaptive answers do not count as independent positive mastery evidence. Public tests are visible formative checks, not exhaustive grading. Python remains in a disposable browser Worker with the existing deadlines and output bounds; learner code is never executed on the application server. C++ and prior visualizers are unchanged. No accounts, backend service, paid API, or hosted model were added.

## Verification

The final branch ran `npm ci --include=dev`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm run test:e2e`, and `git diff --check`. The 32-file Vitest suite passed 271 tests. The focused DP Playwright suite passed eight desktop/mobile tests. The complete desktop/mobile Chromium Playwright suite passed all 130 tests in 13.4 minutes on the final branch contents. Build statically prerendered `/lessons/dynamic-programming`. Chromium in this container used the documented extracted-library `LD_LIBRARY_PATH` setting. Engine tests use independent breadth-first search for coin counts and brute-force subset enumeration for knapsack, plus staircase and immutability checks.

Automated checks cannot establish learning effectiveness or complete accessibility. Human screen-reader and teaching review remain useful; public Python checks can miss behavior outside their contracts. A restrained V1.6 direction is to study where learners struggle with deriving states and transitions, then improve those explanations after human feedback.
