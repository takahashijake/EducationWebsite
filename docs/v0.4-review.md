## Runtime research and architecture

Selected and exact-pinned **Pyodide 0.29.3**, running **CPython 3.13.2**, after consulting its [Worker documentation](https://pyodide.org/en/0.29.3/usage/webworker.html), [stream API](https://pyodide.org/en/0.29.3/usage/streams.html), and [JavaScript API](https://pyodide.org/en/0.29.3/usage/api/js-api.html). Verified the installed runtime version and `unittest.mock` import directly. This pinned core includes unittest in its standard-library ZIP, so the existing terminal assertions need no network-installed Python package.

`python-runtime.json` and the exact npm dependency agree on the version. `scripts/prepare-python.mjs` checks that agreement and copies the package's core JS, WASM, standard-library ZIP, and lockfile into ignored `public/python/0.29.3/`. npm's lockfile records package integrity. Preparation runs after install and before dev/build; no large generated binaries are committed. The browser fetches same-origin static assets only when a learner requests execution. The core assets total approximately 12 MB before compression; no CDN connection or application-server Python interpreter is needed at runtime.

The small `ExecutionEngine` contract takes source, scripted stdin, optional authored checks, and a deadline, and returns typed lifecycle events and results. The Python adapter owns Worker lifecycle, initialization/execution deadlines, request IDs, output bounds, result validation, and cancellation. The interface is independent of the editor; a future engine can extend its language union and implement the same lifecycle without replacing the workspace or feedback views. C++ execution is not implemented.

Every Run or Run Tests request creates a **fresh Worker and interpreter**, including after successful requests. Completion, error, Stop, timeout, or route disposal terminates it. Starting another lab cancels the current owner, limiting simultaneous lab execution to one Worker per page. Initialization has a 30-second deadline; the execution deadline starts only after readiness and is configurable to 1, 3, or 10 seconds in the UI. A later request replaces a terminated Worker. Old job messages cannot update the current request; unmounted components also discard late callbacks.

`public/python-harness.py` compiles `learner.py` with cached source lines for tracebacks. Run uses `__name__ == '__main__'`. Tests re-execute the learner implementation in a fresh globals dictionary per authored group with `__name__ == '__learner__'`, preventing terminal guards from prompting automatically. Ordinary streams/builtins are restored between groups, but modules/files within a single test request are not a security boundary. stdin is deterministic text followed by EOF. `unittest.mock` can patch the actual builtins used by the learner's functions; no reference helpers are injected into missing implementations.

stdout/stderr use bounded stream chunks, Unicode decoding, and a shared 20,000-character display limit. Source is limited to 24,000 JavaScript string characters and stdin to 4,000 before constructing a Worker. Python tracebacks and per-group errors are separately bounded. Source/input limit, loading error, Worker failure, syntax error, runtime error, test failure, timeout, cancellation, and success have distinct outcomes. A normal successful run does not return passing test rows; incomplete/malformed test responses cannot credit missing authored groups.

## User-visible learning experience

The native textarea keeps the application lightweight and approachable. It provides a Python label, monospace editing, instructions, expected behavior, an optional scripted-input editor, keyboard execution with Ctrl+Enter/⌘+Enter, a deadline selector, Run, Run Tests, Stop, and Reset Code. Tab remains normal focus navigation. Reset and project carry-forward require explicit inline confirmation; focus moves first to the safe cancellation action.

Results remain separated into **Execution result**, **Test result**, and **Learning guidance**. Learners see stdout/stderr, error/traceback details, passed/failed/not-run counts, individual group labels, expected behavior, observed assertion details where authored, deterministic explanations, and existing lesson links. Guidance comes from explicit test/exercise concept mappings, not regex guesses about arbitrary exceptions. Each exercise asks for a prediction and a reflection explaining the correction. Correct finite cases are described as limited local evidence rather than mastery.

## Persistence and compatibility

The new key is **`cs-fundamentals:workspace:v1:<workspaceId>`**, where identities include the stable topic/exercise or project/milestone IDs. Entries contain only `{ version: 1, workspaceId, source }`. Parsing validates version, matching identity, source type, and raw/source bounds, including valid empty code. Unsupported, foreign, malformed, and oversized entries fall back without being rewritten on hydration. Only explicit edits or confirmed replacements save code. Disabled/quota-full storage retains an in-memory session draft with a notice. Cross-tab updates are scoped to each key; simultaneous edits are last-write-wins. Source updates withdraw stale test evidence and cancel active execution. Output, input edits, and test evidence are not persisted.

The existing **`cs-fundamentals:progress:v1`** and **`cs-fundamentals:project:v1:number-guessing`** schemas and interpretations are unchanged; their parsers/providers are unchanged from the baseline. Neither Run nor Run Tests updates them. Completed V0.3 stages still open according to the original reasoning/checklist state; there is no migration or new test gate on old progress. Tests verify legacy JSON is unchanged after new code execution, workspace reloads, and project tests. Planned topics remain excluded from curriculum completion counts.

## Resource and security limitations

A disposable browser Worker is **not a strong sandbox for hostile code** and is not a complete memory-isolation guarantee. Python can access JavaScript in the Worker; same-origin network/storage capabilities remain relevant. A large allocation can exhaust browser resources before termination. Source/output/deadline limits address common accidental mistakes, not malicious resource exhaustion. No secrets or authenticated services are added here. If sensitive authenticated data is introduced later, execution needs a separately controlled origin and reviewed messaging, network, and storage boundaries; COOP/COEP alone is insufficient.

Fresh interpreters isolate independent requests, not hostile code from the browser origin. Within one test request, fresh globals and normal stream/builtin restoration do not isolate arbitrary module/file mutations between groups. Learners can inspect or tamper with client-side checks and messages. Test passing is finite advisory evidence, not independent proof of understanding, an achievement credential, or tamper-resistant grading.

Startup costs remain measurable even with cached assets because each request instantiates a fresh interpreter. Only bundled Python/standard-library functionality needed by the curriculum is supported; there is no package-install UI, interactive terminal emulator, cloud compiler, server-side learner execution, C++/Java, account system, database, public code hosting, AI tutor, or cloud synchronization. The textarea intentionally lacks IDE autocomplete and syntax coloring. Independent cross-browser, assistive-technology, and educational review remains necessary.

## PR Pass reconciliation with the C++ playground

Main at cb75b85 already contains the C++ compiler, WASI execution, CodeMirror editor, exercise catalog and practice progress. Both languages remain available in the same lessons. The add/add execution-types conflict is resolved with language-specific interfaces: existing C++ imports retain types.ts, Python imports use python-types.ts, and common source/input/output limits are re-exported from types.ts. The installation/build/development hooks prepare both runtime asset sets. Generated compiler/Python assets stay ignored; package-lock.json is regenerated from the combined pinned dependencies. Neither reading nor project progress changes format.

Two real reliability defects were reproduced with failing regression tests. Flushed Python stdout/stderr below the worker's old 1,024-character batch threshold disappeared when execution timed out or was stopped. Each decoded write now reaches the parent immediately; UTF-8 streaming state, output prefixes and the total character cap remain intact. The real-runtime browser test requires both flushed streams to survive an infinite-loop deadline. A second test showed that a synchronous failure while dispatching execution escaped the Worker message callback. Dispatch now reports worker-error, terminates the Worker and settles the request instead of leaving it pending until the deadline.

The worker-capture unit check executes the actual Worker JavaScript in a VM and tests immediate writes, split UTF-8 and overflow prefixes; it is not claimed as interpreter verification. The browser suite separately executes real self-hosted Pyodide and real C++ WebAssembly.

The original external scanner's JWT_MISCONFIGURATION finding points to TextDecoder.decode on console bytes; there is no JWT verification in this application. Its SILENT_EXCEPTION finding points to an initialization catch that posts load-error to the parent; the browser retry test exercises this path. No scanner suppression, status override or branch-rule change is used. A failed final external check remains a merge blocker under the PR Pass instructions.
