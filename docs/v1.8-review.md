# V1.8 implementation review

## Learner journey and educational rationale

The published Weighted Graphs and Shortest Paths lesson now links **Predict → Explain → Implement → Transfer → Revisit** around one claim: when Dijkstra removes the valid minimum-distance queue entry, that vertex's distance is final if all edges are nonnegative. The journey appears in lesson navigation and leaves other lesson content available. A learner predicts the next valid settlement from an authored graph state, submits their own explanation before seeing a five-point proof rubric, edits and tests the existing `weighted-dijkstra` Python exercise, solves a directed transit network, and may return after 24 hours for a negative-edge case.

Prediction requires both a selected transition and a reason. The two prediction graphs exercise a cheaper detour and a zero-weight improvement with an obsolete queue entry. Their displayed state and answer come from `generateWeightedSteps`, the same deterministic engine as the existing player. A wrong choice receives cautious, specific feedback and a lesson link. The explanation is saved and self-reviewed; the site never grades prose by keyword matching. The model proof identifies the valid heap minimum, settlement, nonnegative weights, why a later route cannot be cheaper, and why a negative edge breaks the argument.

Initial transfer uses one of two network structures: a free interchange that improves an earlier tentative distance, or two equal-cost routes with an unreachable vertex and a stale direct entry. The evaluator uses the existing graph validation and trace for optimal cost, checks each entered directed edge, and accepts **either** optimal equal-cost route. The delayed case asks whether Dijkstra is suitable when a negative edge could improve an already settled vertex. It has a different graph and task form. These cases are separate from the prediction graph and Python public-test fixtures. The learner writes a justification in each transfer case; only the structured route/action is checked automatically, while authored reasoning is shown for self-review.

## Reused contracts and architecture

`src/content/invariant-journey.ts` holds authored scenarios, explanations, and a thin evaluator over `weighted-graph-steps.ts`. `src/lib/invariant-journey-state.ts` validates bounded journey data and the injectable 24-hour clock rule. `use-invariant-journey.ts` handles browser storage, same-tab and cross-tab updates, and session-only fallback. `InvariantJourney` renders the stages and embeds exactly one existing `CodeLab` for `weighted-dijkstra`. The other weighted Python labs remain available in the lesson. The Code Lab reports current public-check results to its parent and withdraws them after edits, cancellation, failed execution, or a cross-tab source change; its existing Worker, tests, exercise ID, saved workspace, and evidence recording remain in place.

The separate `cs-fundamentals:invariant-journey:v1` record stores a versioned seed, authored prediction, explanation, bounded transfer attempts, and revisit attempts. It rejects malformed, oversized, unsupported, and inconsistent records. The first transfer attempt starts the 24-hour interval; a backward device clock does not make the revisit early. Hints mark an attempt assisted. Restart starts a new journey variant and does not clear the Python draft or existing V1 learning evidence. Journey transfer outcomes stay **formative in their companion record**: no new mastery activity is inferred from route selection or ungraded writing. A successful Code Lab public test retains its existing limited evidence semantics and is never counted a second time by the journey.

## Accessibility, security, and deployment

Stage buttons are keyboard-operable with `aria-current`, headings receive focus on navigation, and feedback has a focused status region. Forms use labels and fieldsets. CSS wraps the stage controls and graph edges on narrow screens; the journey introduces no animation. The Code Lab continues to run learner Python in the existing browser Worker with its source, time, and output limits. No server code execution, new dependency, account, LLM service, or CSP relaxation was added. Build-time `NEXT_PUBLIC_APP_BASE_PATH` remains the same mechanism for root and subpath deployment.

## Limits and next steps

This is one invariant with authored, bounded cases. The journey does not trace arbitrary learner Python, grade free-text reasoning, verify every possible Python implementation, or send revisit reminders. A public-code pass, self-review, successful route, or delayed revisit does not establish mastery. Browser-local progress is not portable across devices. Automated tests verify deterministic behavior and compatibility; they **cannot establish improved learning outcomes**. Conduct educator review, learner think-aloud studies, and human assistive-technology testing before extending the pattern to Dynamic Programming or Trees.

The revisit interval uses the device clock. Attempts dated before the first transfer are rejected, and moving the clock backward does not open the revisit. Moving it forward can make a browser-local interval appear to have elapsed. Enforcing elapsed real time across reloads requires a trusted time source; this formative prompt does not provide one.
