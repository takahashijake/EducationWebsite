# Authored misconception mapping rubric

Use this checklist before adding a stable misconception ID. An answer is **a possible signal**, not a diagnosis of the learner's thinking.

1. State the published skill and the precise concept tested. Keep its existing skill and activity IDs.
2. Name the incorrect reasoning represented by a **specific distractor**. Verify the option is wrong for every generated seed. If several lines of reasoning could produce it, leave `misconceptionId` unset and show only ordinary answer feedback.
3. Explain why that answer is wrong and give the correct rule without implying certainty about the learner. Avoid “you believe…” language.
4. Write a concrete contrast that differs at a boundary where the tempting rule and correct rule produce different results. Check both outcomes manually and in tests.
5. Choose a different authored family and a qualifying case tag for an independent follow-up. It must probe the same concept at a discriminating boundary with a different task form, not only changed numbers or nouns. Make sure hints and revealed solutions still prevent independent positive evidence under existing rules.
6. Give a published lesson link, stable ID and catalog revision. Validate source family/skill/revision and follow-up family/skill, and generate many seeds to verify option mapping.
7. Test ambiguous options, repeated signals, different signals within one skill, stale revisions, malformed storage, and independent versus assisted follow-up. Review wording with a CS educator and test comprehension with learners before broad rollout.

V1.7 maps only `comparison-policy` choices that confuse strict `>` with inclusive `>=`. The `==` distractor is deliberately unlabeled because its reason is not uniquely supported by that choice. The counterexample at the exact boundary distinguishes these operators. `comparison-branch` asks the learner to evaluate a branch rather than select a symbol.
