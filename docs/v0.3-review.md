## Delivered behavior and educational decisions

- Publish **Recursion** and **Basic Debugging** at their existing `/lessons/recursion` and `/lessons/debugging` URLs. Nine lessons are now published; 37 topics remain planned. All seven Programming Fundamentals topics are available.
- Extend the programming path in existing curriculum order: Variables → Operators → Conditionals → Loops → Functions → Recursion → Debugging. Debugging's advisory prerequisite remains Functions. Path validation requires all referenced prerequisites to precede a lesson, rather than inventing a conceptual dependency on the immediately previous lesson.
- Recursion explains definitions, base/recursive cases, decreasing measures, stack depth, separate local variables, pending work, unwinding, return propagation, and iterative alternatives. Factorial scenarios cover 3, 0, 1, and 4; summation and recursive search cover additional patterns and empty/missing boundaries.
- Debugging teaches syntax/runtime/logical failures, traceback interpretation, caller input investigation, scope/state tracing, minimization, hypotheses, threshold/range boundaries, focused repairs, and retained regression tests. The trace compares buggy/fixed inclusive sums on ordinary and smallest positive cases. Three exercises include output/repair reasoning and a runtime traceback investigation.
- Use one existing trace player for both lessons. Recursive examples author unique invocation IDs/scopes, suspended callers, inspectable returns, and reverse-order restoration. No result is bound in the module before its right-hand call returns. Python instrumentation checks calls/returns and accumulator updates against snapshots.
- Add a generic project schema, catalog, static project routes, renderer, content validation, and independent browser progress hook. The first project builds comparison, conversion/range validation, a bounded round, a regression test, and a terminal adapter.
- Project prerequisites are advisory, while milestones are sequential. Each stage has a contract, starter, links to prior concepts, incremental hints, a reasoning question, a worked solution after an attempt, runnable deterministic tests, and self-reported local-work checks. A final reference is available only after all stages. Undoing an earlier checklist item closes later stages and hides the final reference; saved downstream work is retained for when prerequisites are restored.
- Keep the secret fixed at 12 and inject finite text entries into the engine for reproducible behavior. Invalid entries do not count as attempts. Test zero work, conversion failure, range boundaries, success, input exhaustion, and a winning guess just outside the budget. The terminal adapter reuses the helpers and handles end-of-file.
- Add a shared visit-level assessment summary using optional result callbacks in the existing practice/quiz components. It counts attempted/correct checks and suggests revisiting explanation/practice. Retrying withdraws the current attempt. Reading completion is still a separate manual action; neither completion nor correct fixed questions are called mastery.
- Retain responsive code scrolling, native radio/checkbox/disclosure interactions, visible focus (including new disclosure summaries), wrapped controls, and keyboard trace/hint/solution activation. No dependencies, arbitrary-code execution, AI services, authentication, or payment infrastructure were added.

## Persistence and compatibility

`src/lib/progress.ts` and `progress-provider.tsx` remain unchanged. Existing `cs-fundamentals:progress:v1` JSON is not migrated or rewritten on load. Original three completions remain byte-for-byte intact on initial rendering; global reading progress becomes 3/9 (33%), and path progress becomes 1/7 (14%). Tests also cover completion/undo and real cross-tab synchronization. Still-planned topic IDs cannot inflate completion. Projects never add to lesson denominators.

The per-project key `cs-fundamentals:project:v1:number-guessing` stores version 1, project identity, submitted question indices, and checked item IDs. Defensive parsing rejects malformed/unsupported/foreign payloads and filters invalid indices, unknown IDs, and duplicate checks. Stage states are recomputed from current questions, local-work checks, and prior stages, ignoring any alleged stored completion flag. The hook reads the latest store before updates, uses a deterministic server snapshot, listens for storage events, and does no load-time writing. Denied writes produce a session fallback and an explicit notice, including after remounting the project. Hint/disclosure visibility is not persisted.

## Limits and next milestone

The browser checks authored choices; students implement and run Python locally. Project completion combines reasoning checks with self-reported local work. It is not an independent coding assessment or credential. Lesson assessment attempts last for the current visit only. Persistence is browser/origin-local, without cloud backup or transactional same-instant writes across tabs. Structural trace validation cannot establish arbitrary Python semantics; the targeted Python checks cover this catalog's examples. Chromium desktop/mobile coverage does not replace independent teaching, screen-reader, or cross-browser review.

Recommended V0.4: concept-tagged assessments and transparent knowledge-gap diagnosis with delayed retrieval practice and targeted review links. Add a small independent project variation and an explicit rubric before extending into a larger adaptive platform or expanding the curriculum. Arrange human educational and accessibility review of the complete programming loop.
