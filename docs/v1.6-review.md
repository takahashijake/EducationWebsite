## Confirmed behavior and fixes

- A normal hydrated click on a C++ exercise exposed its editor in the baseline browser check. A direct `#cpp-variables-output` link left the `<details>` closed. With JavaScript disabled, native `<details>` exposed the worked example and task but not the conditionally rendered playground. These two cases reproduce the misleading incomplete activity. The exact cause of the reported student's session is unknown; a client hydration failure or disabled JavaScript could produce the same visible state.
- The playground is now part of the panel's initial render and remains mounted across repeated expansion. A targeted hash opens its panel on load or hash navigation. A loading message, plain textarea fallback for CodeMirror initialization failure, and `noscript` recovery text prevent a silent missing workspace. Existing draft, attempt, cancellation, and stale-result contracts remain in place.
- Public C++ and Python resources had origin-root URL literals. The build-time `NEXT_PUBLIC_APP_BASE_PATH` config now gives Next.js its `basePath`; a small helper prefixes public Worker/runtime URLs only once. The Python harness resolves relative to the Worker location. C++ module imports and browsercc runtime imports were already relative to their Worker/module URL, so they retain same-origin loading under a prefix. Next.js handles its own links, CSS, and JavaScript chunks.
- The first C++ activity now names the action, says what code to edit, where to enter input, and how Run and Submit differ. Shared C++ workspace copy identifies editable code, example output, actual standard output, and feedback. No permanent IDs or evidence keys changed.

## Compatibility and security

- `basePath` is embedded at build time; the proxy must forward the prefixed path to Next.js. Root hosting remains the default. The configuration validates path syntax and does not add an asset CDN or permissive development origins.
- The [Next.js basePath documentation](https://nextjs.org/docs/pages/api-reference/config/next-config-js/basePath) confirms build-time inlining and automatic prefixing for Next links. The [Jupyter Server Proxy documentation](https://jupyter-server-proxy.readthedocs.io/en/latest/arbitrary-ports-hosts.html) confirms that its `proxy/absolute` form forwards the full URL path. The proxy-shaped browser test uses those path semantics directly against Next.js; it does not exercise a live JupyterHub installation.
- The C++ Worker CSP, WASI import allowlist, 64 MiB learner-program memory cap, compile/run deadlines, output limits, and cancellation remain unchanged. Python continues to use disposable same-origin Workers. Public checks are formative, not hidden certification.
- Existing V1 browser storage records and evidence semantics are unchanged. Browser storage is scoped to the origin; a new origin does not automatically receive old drafts.

## Remaining limits

- A direct Next.js subpath test can verify its asset behavior but cannot certify a particular external proxy's rewrite, cookie, or WebSocket settings. The JupyterHub absolute-proxy route shape is used only as a generic path fixture, with no usernames or infrastructure values in production code.
- A page with JavaScript entirely disabled can read the activity and see recovery instructions, but cannot run browser Workers. The CodeMirror fallback covers editor initialization errors after JavaScript starts, not arbitrary bundle download failure.
- First compiler transfer remains about 95 MB. Progress messaging names the download and compile phase; it does not report an exact byte percentage because browsercc does not expose one.
- Chromium's temporary browser cache may decline to store the large compiler WASM even when execution succeeds; the download remains usable for that run.
