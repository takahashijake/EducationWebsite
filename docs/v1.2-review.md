# V1.2 review: Trees, binary search trees, and recursive reasoning

## Educational scope

The existing `trees` ID and `/lessons/trees` route are published with advisory Recursion, Stacks and Queues, Linked Lists, and Big O prerequisites. The lesson distinguishes general trees, binary trees, and BSTs; teaches root, parent, child, sibling, leaf, subtree, depth, levels, shape, identity, and edge-based height; and provides worked traversal and deletion examples. Related lessons are linked from the lesson. Three explanatory knowledge checks, misconceptions, a live player, six Python Code Labs, retrieval, and adaptive practice use the existing lesson and evidence systems.

Height is the greatest number of **edges** from a node to a leaf: empty tree -1, leaf 0, singleton tree 0. Depth counts edges from the root, whose depth is 0. Nodes at the same depth form a level. A balanced-looking tree has a shorter path than a chain, but ordinary BST insertion does not maintain balance.

## Ordering, traversal, and mutation contracts

The strict global BST invariant applies at **every** node: all keys anywhere in its left subtree are smaller, and all keys anywhere in its right subtree are larger. Keys are unique bounded integers. Duplicate insertion is a no-op, including at the root; it does not replace an object or add an equal-key child. Search chooses one child per comparison and returns absent at the selected empty reference. Minimum follows left children; maximum follows right children.

Preorder visits node, left, right. Inorder visits left, node, right. Postorder visits left, right, node. Recursive frames remember where to resume after a child returns. Level-order uses a FIFO queue and visits left before right at each depth. Inorder produces sorted keys **only when** strict BST ordering already holds. An empty traversal returns an empty order.

Leaf deletion removes the parent's reference. One-child deletion connects the surviving child to the deleted node's parent. Root deletion changes the root reference. Two-child deletion finds the existing minimum node of the right subtree, detaches it, connects any right child at its old position, and **transplants that same node object** into the deleted node's position. The removed node's identity disappears; the successor's ID and key stay together. No key copy into the deleted object is implied by the engine, diagram, or Python reference.

Search, insertion, and deletion take O(h) time for tree height h, typically O(log n) on a reasonably balanced shape and O(n) on a maximally skewed ordinary BST. The n nodes occupy O(n) storage. Recursive depth-first operations use O(h) call-stack space; level-order queue space is at most O(n); iterative search uses O(1) auxiliary space. These costs refer to different resources. The player additionally validates whole trees and copies snapshots, so its runtime is not a benchmark of the underlying O(h) operations.

## Deterministic player and limits

`src/lib/tree-steps.ts` is React-independent. It validates one root, unique `n` IDs, safe integer keys from -999 through 999, strict ordering, reachable nodes, references, and a monotonic `nextId`. It rejects cycles, shared children, dangling references, repeated IDs, malformed inputs, and unreachable nodes. Construction accepts at most 16 key operations; the player allows at most 16 composed insert/delete actions and 12 active nodes. A trace has at most 128 steps. Each snapshot owns its full tree and copies its path, visited IDs, recursive frames, FIFO queue, comparison, narration, invariant, and outcome. Later mutations do not rewrite earlier snapshots. The engine never evaluates user source.

The player offers empty, singleton, balanced, skewed, duplicate, and three deletion scenarios. It shows an SVG with stable IDs and parent-child edges, a text structure list, operation state, step controls, and a prediction before reveal. Predictions explain the next compared, visited, or structurally selected key; they reset on scenario or operation changes and do **not** create positive concept evidence. Keyboard controls, labels, live narration, reduced-motion CSS, and a single-column mobile layout support access without relying on color alone. The textual structure remains useful when the full diagram is visually dense.

## Remaining gaps and V1.3 direction

This milestone does not implement AVL or red-black balancing. The player is bounded and traces its own BST, not learner Python; it cannot represent every general-tree shape. Human screen-reader and teaching review remain useful beyond automated Chromium coverage. A sensible V1.3 path is self-balancing trees or weighted graph paths, with careful review of reference identity and algorithmic invariants before expansion.
