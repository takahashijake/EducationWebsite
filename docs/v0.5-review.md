## Architecture and data contracts

`src/content/learning-catalog.ts` declares 15 stable, fine-grained skills across all seven published Programming Fundamentals lessons. Each has a published topic destination and explicit prerequisites. Explicit question-to-skill mappings cover the integrated assessment, all seven lesson checks, and existing authored Python labs. `src/content/learning-catalog-validation.ts` compares the lightweight client metadata with full authored lesson and exercise definitions and checks duplicate IDs, references, published destinations, question shape, and prerequisite cycles. Existing Python `conceptIds` remain **topic IDs** for instructional links; the diagnosis mapping is separate and explicitly named. The catalog includes 25 independently authored retrieval questions, with more than one for several core skills, and avoids planned topic destinations.

`src/lib/learning-evidence.ts` owns the independent `cs-fundamentals:evidence:v1` store. Records contain only `{attemptId, activityId, source, correct, at, revision}`. Skill IDs come from the authored activity catalog rather than untrusted record contents. Timestamps are canonical ISO UTC. Parsers reject unsupported versions, malformed or oversized payloads, unknown activities, source/revision mismatches, invalid timestamps, and duplicate attempt IDs; they discard unknown fields. The most recent 240 records are retained. A revision mismatch is ignored rather than treated as current evidence; authors must bump an activity revision when a change alters what success means. Unknown or old records do not rewrite storage during hydration.

`src/components/use-learning-evidence.ts` uses `useSyncExternalStore` for same-tab updates and `storage` events for cross-tab updates. Writes occur only on explicit submissions or clearing. If local storage rejects writes, an in-memory fallback supports the current client session and the UI discloses that limit. The previous reading, project, C++ practice, and workspace keys are unchanged. Clearing evidence leaves reading completion and code drafts alone. There is no account or cloud copy, and the evidence store never contains learner source code.

The integrated assessment and lesson knowledge checks record one outcome per authored question after a complete submission. Retrying a quiz appends new observations; it does not erase earlier attempts. Python lab evidence is recorded only after all authored test rows return and the request is current. Normal Run, partial results, cancellation, timeout, source edits, and stale worker responses are excluded. Multi-skill test submissions are partial evidence. C++ execution continues using its independent practice progress; C++ tests are not mapped to fine-grained V0.5 skills yet.

## Diagnosis and recommendation rules

`diagnose` and `recommend` are pure functions with an injectable timestamp. A skill with no focused question is **Not yet assessed**, even if a combined question involved it. A latest incorrect focused result is **Needs review**. Otherwise focused observations begin at **Practicing**. **Reinforced through repeated evidence** requires correct focused responses to two distinct activities plus a correct retrieval response at least 24 hours after the first success, with no later focused mistake. The strongest state is still limited evidence, not mastery. A recent incorrect multi-skill response adds a review clue and prioritizes a focused question without definitively blaming every mapped skill. The dashboard gives counts, recent observation names, dates, and plain-language reasons; it does not invent confidence percentages.

Recommendations sort deterministically: recent focused or combined mistakes; due reviews; a relevant prerequisite currently needing review; unassessed foundations; then continued practice. Catalog order breaks ties. An unseen authored retrieval item is preferred; a seen item is identified as a retry. No recommendation locks access to advanced lessons. The clock excludes records more than five minutes in the future so a mis-set device clock cannot create immediate reinforcement. The schedule is an authored heuristic, not a personalized forgetting curve: one day after focused success, then three, seven, and fourteen days after successive successful delayed retrievals. A retrieval only advances the schedule when it succeeds at or after the prior due time; rapid retries remain practice observations without compressing review sessions. A focused mistake makes review due immediately and resets the successful evidence streak; after a correct recovery, the interval returns to one day. Duplicate attempt IDs count once, and observations are processed by timestamp. No background task or notification is used. Returning to `/learning` computes due activities from saved timestamps.

`src/components/retrieval-practice.tsx` offers keyboard-accessible, labeled questions, answer feedback, contextual published lesson links, a retry, and a new-question action. It moves focus to feedback after submission and to the answer control after a retry. `src/components/learning-insights.tsx` separates reading, evidence-backed understanding, struggle explanations, and the next direct action. The evidence-clear confirmation focuses its safe action. Text states and reasons remain legible without color or charts; responsive panels stack on mobile. Empty profiles provide assessment and practice entry points.

## Transfer challenge and security boundary

`src/content/transfer-challenge.ts` defines the independently authored expense-summary task. Learners implement validation, a loop, accumulation, a function return, and a strict boundary check from incomplete code. Five public test groups cover empty input, exact equality, over-limit totals, negative amounts, and negative limits. Optional progressive hints and a self-explanation prompt are shown by the existing `CodeLab`. A reference solution is used for authoring verification and is not loaded as the starter. The route `src/app/practice/transfer/page.tsx` reuses the same Python Worker, saved workspace, and test harness. Passing public tests is finite practice evidence; it is not trusted grading.

The Python Worker does **not** safely isolate hostile code. Browser-public assertions can be inspected or tampered with. The existing C++ WASI and Python Worker boundaries, execution limits, and absence of server-side learner execution remain unchanged. Future authenticated features would require a separate security review and execution origin.

## Authoring new content

1. Add a stable skill to `src/content/learning-catalog.ts` with a published topic ID, prerequisite IDs, and a useful lesson destination. Keep IDs stable; do not repurpose a topic-level `conceptIds` value.
2. Add an independently written retrieval question with one or more explicit `skillIds`, a clear explanation, and a revision. Prefer focused single-skill questions when the goal is diagnosis. Include boundary and misconception distractors that reveal reasoning, and add another variant for repeated practice.
3. Map any assessment, lesson, or code activity explicitly in the catalog. Bump its revision if the meaning of a correct outcome changes. Run the catalog integrity test and the full suite.
4. Check a correct reference and an intentionally wrong variant against actual Python where code is involved. Treat public checks as learner feedback, never as a secure grade.

## Limits and next direction

Multiple-choice answers reveal only the prompted reasoning; a combined miss cannot identify a single cause. A learner can memorize public questions or tests. There is no identity, cross-device synchronization, notification, adaptive content generation, or tamper-resistant certification. Browser clock changes can shift due dates. History is intentionally bounded, so old observations eventually leave the profile. The next extension should author skill registries and independent retrieval sets for Data Structures and Algorithms, preserving published topic IDs and keeping new domain evidence explicit. More transfer tasks and authored misconceptions would improve diagnostic breadth before adding complex scoring.
